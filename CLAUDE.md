# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```
npm install       # install dependencies
npm run dev       # start Vite dev server (http://localhost:5173)
npm run build     # tsc -b type-check, then vite production build
npm run preview   # serve the production build locally
```

There is no lint script and no test suite configured — `npm run build` (which runs `tsc -b` with `strict`, `noUnusedLocals`, `noUnusedParameters`) is the only automated correctness check. Node/npm may not be on `PATH` in a fresh shell on this machine even when installed — if `node`/`npm` aren't found, check `C:\Program Files\nodejs` directly before assuming they're missing.

## Architecture

AutoProva is a client-only SPA (Vite + React + TypeScript + Tailwind, dark theme only) that generates an academic exam (default 10 questions, configurable) from a teacher's prompt using an LLM, rendered as HTML and exported as a real PDF — there is no LaTeX/Overleaf pipeline. **There is no backend** — the browser calls the selected provider's API directly. The user picks a provider (Anthropic/Claude or Google/Gemini) in `ConfigPanel`, enters that provider's own API key, and both are persisted only in `localStorage` (one key per provider, so switching providers doesn't lose the other's key — see `DEFAULT_API_KEYS`/`autoprova_api_keys` in `App.tsx`).

### Multi-provider LLM layer

[src/lib/llmProviders.ts](src/lib/llmProviders.ts) is the provider registry: `LLM_PROVIDERS` lists each provider's id, label, API-key placeholder/help text, and available models; `getProviderConfig()`/`defaultModelFor()`/`isValidModelFor()` are used by `ConfigPanel` (to render the provider + model dropdowns, the model list changing with the selected provider) and by `App.tsx` (to fall back to a valid model when the persisted one doesn't belong to the current provider, e.g. after switching providers). Adding a new provider means adding an entry here, a `call<Provider>()` function in `llmClient.ts`, and a branch in `callLlmTool()`.

[src/lib/llmClient.ts](src/lib/llmClient.ts) (formerly `anthropicClient.ts`) is provider-agnostic at the call-site: `generateExam(provider, apiKey, model, ...)` and `editQuestion(provider, apiKey, model, ...)` both take a `provider: LlmProvider` and dispatch via `callLlmTool()` to either `callAnthropic()` (Anthropic Messages API, forced tool-use via `tool_choice: {type:'tool', name}`, response parsed from the `tool_use` content block) or `callGemini()` (Gemini `generateContent` REST endpoint, forced function-calling via `toolConfig.functionCallingConfig.mode: 'ANY'`, response parsed from the `functionCall.args` part). Tool/schema definitions ([src/lib/examTool.ts](src/lib/examTool.ts), [src/lib/questionEditTool.ts](src/lib/questionEditTool.ts)) are written once in Anthropic's `input_schema` shape (JSON Schema, lowercase `type`); `toGeminiSchema()` in [src/lib/schemaConvert.ts](src/lib/schemaConvert.ts) converts that same schema into Gemini's `Schema` format (uppercase `type`, no `minItems`/`maxItems`) at request time — there is no second, hand-maintained schema for Gemini.

### Data flow

1. `App.tsx` holds all state: `provider`/`apiKeys` (per-provider, see above)/`model`/`header` (persisted via `useLocalStorage`), and `prompt`/`numQuestoes`/`exam`/`loading`/`error` (session-only `useState`).
2. `handleGenerate` calls `generateExam()` in [src/lib/llmClient.ts](src/lib/llmClient.ts), which dispatches to the selected provider's API as described above.
3. Structured output is enforced via forced tool-use/function-calling in both providers, not freeform JSON parsing: [src/lib/examTool.ts](src/lib/examTool.ts) exports `buildSystemPrompt(numQuestoes)` and `buildExamTool(numQuestoes)`, which build the Portuguese system prompt and the `gerar_prova` tool schema (with `minItems`/`maxItems` pinned to `numQuestoes`, honored by Anthropic — dropped by the Gemini conversion, which relies on the prompt instructions instead) for the requested question count. The parsed tool-call input _is_ the `ExamData` object (after `sanitizeExamData()` strips a stray `{,}` decimal-comma artifact the model occasionally emits) — no `JSON.parse`/markdown-fence stripping needed.
4. `ExamData` (shape in [src/types.ts](src/types.ts)) and `HeaderInfo` flow into [src/components/ExamPaper.tsx](src/components/ExamPaper.tsx), a single `forwardRef` component that is the **one source of truth** for what the exam looks like — math is rendered via KaTeX through the `MathText` component. There is deliberately no second, hand-maintained template: an earlier LaTeX-template version of this app let the LaTeX output drift out of sync with the on-screen preview, which is why the app renders everything from this one component. When `editable` (only passed for the "Prévia da Prova" tab, and only takes effect when `mode === 'prova'`), the same component also becomes the editing surface (see below) — the "Prévia do Gabarito" tab renders it with `editable` unset, so that view stays exactly the plain read-only answer key.
5. `ResultPanel` shows two tabs ("Prévia da Prova" / "Prévia do Gabarito"), both backed by the same `PreviewDocument`/`ExamPaper` pair — only the `mode` prop (`'prova'` vs `'gabarito'`) differs, so the two views can never drift out of sync with each other. Each tab derives its downloaded PDF file name from `buildDownloadFileName()` in [src/lib/fileName.ts](src/lib/fileName.ts), which combines `header.tipo`/`turma`/`valor` and `exam.assunto` (plus a "Gabarito" suffix in that mode) and strips filesystem-illegal characters. There is no raw-HTML export view — an earlier "Código HTML" tab (`HtmlCodeView`/`htmlExport.ts`) was removed as unneeded. Since PDF export is generated independently from `ExamData` (see below, not by capturing the DOM), the editing affordances described next only ever appear on screen and never leak into the exported PDF.

### In-place question editing

There are two equivalent ways to edit questions, and both are kept in sync because they share the exact same mutation logic: [src/hooks/useExamEditor.ts](src/hooks/useExamEditor.ts) holds all of it (add/remove/reorder questions, change `tipo`, alternativas, `respostaCorreta`, `imagem`, `enunciadoStyle`, and the two AI-assisted actions) as a plain hook consumed once in `App.tsx`; the returned `ExamEditorHandlers` are passed to *both* consumers below, so neither one duplicates a mutation and the two can never drift apart.

1. **Direct on the preview** — WYSIWYG editing on the "Prévia da Prova" tab. `ExamEditorHandlers` are threaded down through `ResultPanel` → `PreviewDocument` → `ExamPaper`, which renders the interactive controls inline (a per-question hover toolbar for `tipo`/AI-edit/remove, a clickable dot per alternative to set `respostaCorreta`, a click-to-add/edit/remove-image affordance, and an "add question" bar after the last question) only when `editable` — the non-editable render path is a byte-for-byte identical fallback to plain `MathText`/static `<img>`, so the gabarito/read-only view can never regress. [src/components/EditableText.tsx](src/components/EditableText.tsx) is the "click to edit" primitive used for `enunciado`/`alternativa.texto`: it shows the rendered `MathText` until clicked, then swaps to a plain `<textarea>` with the raw text (including `$...$` syntax, since making KaTeX's rendered HTML itself editable isn't safe), with a small toolbar (shown only while editing) for Bold/Italic/Underline/font-size (A-/A+, all applied to just the current textarea selection — not the whole field) plus, on the enunciado instance only, paragraph alignment buttons — and commits on blur.
2. **[src/components/QuestionEditor.tsx](src/components/QuestionEditor.tsx)** — a traditional form-based side panel (right column, `2xl:` breakpoint and up; below that it collapses under the preview), for teachers who prefer a plain list of fields over clicking into the preview. It has no rich-text toolbar (kept intentionally simple, matching what it looked like before the WYSIWYG preview existed) but drives the exact same handlers, so e.g. marking a correct answer here instantly updates the preview's dot/GABARITO and vice versa.

The AI-assisted actions (available from both surfaces) go through `editQuestion()` in `llmClient.ts` (same `callLlmTool()` dispatcher as `generateExam()`, but with the `editar_questao` tool schema/system prompt from [src/lib/questionEditTool.ts](src/lib/questionEditTool.ts)) via the shared [src/components/AiPanel.tsx](src/components/AiPanel.tsx) popover, sending the exam's `assunto` plus the current question (if editing rather than adding) as context. Question numbers are always kept contiguous via `renumerar()` (inside the hook) so the printed GABARITO stays in sync. Both this tool's output and `generateExam()`'s output are run through the same `stripBracedComma()` sanitization for the `{,}` artifact.

### Inline text formatting (bold/italic/underline/size/alignment)

Bold/italic/underline/font-size are markers embedded directly in the raw `enunciado`/`alternativa.texto` string — `**bold**`, `*italic*`, `__underline__`, `[[1.30]]bigger[[/]]` — the same trick already used for math (`$...$`), so no data-model migration was needed and the AI still reads/writes plain text. [src/lib/richTextRuns.ts](src/lib/richTextRuns.ts) exports `parseFormattingRuns()` (turns a non-math text segment into `{text, bold, italic, underline, fontScale}` runs), `toggleWrap()` (binary bold/italic/underline: wraps/unwraps the current textarea selection with a marker), and `adjustFontScale()` (font size is a continuous value, not binary, so instead of toggling it adjusts the existing `[[N]]...[[/]]` wrapping the selection by ±`FONT_SCALE_STEP`, or wraps fresh if the selection isn't already exactly one — this is what makes the A-/A+ toolbar buttons resize **only the selected text**, not the whole field). Both `MathText.tsx` (screen) and `examPdf.ts` (PDF, via `styledRunsFromRichText()`) apply `parseFormattingRuns()` **after** splitting on `$...$`, never before — so a marker can never be interpreted inside a formula, and a formula can never sit mid-marker; this ordering must stay identical on both sides or the two renders will visibly diverge (see `mathSegments.ts` for the shared math-splitting step). Alignment is the one paragraph-level (not per-character) property — stored as `Questao.enunciadoStyle?: { align }` ([src/types.ts](src/types.ts)) and applied only to the enunciado (alternatives are too short to need it) as an inline `style` on the wrapping `<p>` in `ExamPaper.tsx`; on the PDF side it's passed to `richText.ts`'s `drawLines()` for that paragraph. Font scale, being per-run, flows through `StyledRun.fontScale` all the way into `richText.ts`'s `WordToken`/line-height calculation, so a line containing one enlarged word is measured/drawn tall enough for it without affecting neighboring lines.

### Visual image editor

[src/components/ImageEditorModal.tsx](src/components/ImageEditorModal.tsx) opens from the click-to-add/edit-image affordance in `ExamPaper.tsx` and edits `Questao.imagem` as a small SVG document. [src/lib/svgEditor.ts](src/lib/svgEditor.ts) is the structural model: an SVG is parsed into a list of typed `SvgShape`s (rect/circle/ellipse/line/curve/polygon/text/path, plus a `raw` fallback for anything unsupported so the editor never loses content on save) and serialized back to the same SVG string format accepted by `Questao.imagem`. Every shape (except text, which is a single click to place) is drawn by clicking a toolbar button to arm that tool, then click-dragging directly on the canvas (`createShapeFromDrag()`); the editor returns to select mode after each shape so an armed tool never draws twice by accident. The freehand brush tool (`createFreehandShape()`) samples pointer-move points and smooths them into a quadratic-Bézier path via `buildSmoothPathD()`; the curve tool is a `CurveShape` (two endpoints + a control point) with its own draggable on-canvas handle, serialized as a `<path>` carrying `data-shape="curve"` plus `data-x1/y1/x2/y2/cx/cy` attributes so `parseSvgDoc()` can reconstruct the typed shape on reopen — a `<path>` without that marker still falls through to the generic, move/recolor-only `path` type, so imported or AI-generated SVGs are unaffected. Every stroke-capable shape also has a `strokeDasharray` (solid/dashed/dotted, picked from the property panel's "Estilo do traço" select).

### PDF export

`PreviewDocument`'s "Baixar PDF" button calls `generateExamPdf()` in [src/lib/pdf/examPdf.ts](src/lib/pdf/examPdf.ts), which draws real vector text via `jsPDF` — the PDF text is selectable/copyable, unlike an earlier version of this app that rasterized the whole `ExamPaper` DOM node via `html-to-image` and embedded it as an image. Because a second "template" (jsPDF drawing calls) now exists in parallel to `ExamPaper.tsx`'s DOM/CSS rendering, pure logic and literal strings are shared between the two via [src/lib/examContent.ts](src/lib/examContent.ts), [src/lib/mathSegments.ts](src/lib/mathSegments.ts), and [src/lib/richTextRuns.ts](src/lib/richTextRuns.ts) — only the actual drawing code is duplicated, since DOM/CSS and jsPDF primitives are incompatible paradigms. Math (`$...$`) is rasterized per unique formula via KaTeX + `html-to-image` ([src/lib/pdf/mathRaster.ts](src/lib/pdf/mathRaster.ts)) and embedded as an inline PNG sized proportionally to the surrounding font size; images (school logos, question images, including inline `<svg>`) are rasterized the same way via [src/lib/pdf/imageRaster.ts](src/lib/pdf/imageRaster.ts), with a failed/broken image silently skipped rather than aborting the whole export. [src/lib/pdf/richText.ts](src/lib/pdf/richText.ts) is a domain-agnostic word-wrap engine (`tokenizeRuns`/`layoutParagraph`/`drawLines`) that mixes text tokens and math-image tokens in one line-breaking pass, supports a per-line max-width function (so the GABARITO box can narrow the first few lines like a CSS float) and per-paragraph alignment/underline; `examPdf.ts` measures each question block before drawing so it can force a page break without ever splitting a question across two PDF pages.

### Header metadata vs. AI-generated content

`HeaderInfo` (`professor`, `turma`, `tipo`, `disciplina`, `valor`) are plain user-filled form fields (`HeaderFieldsForm`); the school's own info (name, address, phone, email, logos) is managed separately per school in `schoolInfo.ts`/`SchoolFormModal` (add/edit/select a school, persisted in `localStorage`) rather than typed into the header form each time. Neither is sent to or generated by Claude — only the questions/alternatives come back from the model. The exam title shown/printed is computed deterministically by `buildExamTitle()` in [src/lib/examTitle.ts](src/lib/examTitle.ts) from `tipo`/`disciplina`/`valor` (e.g. "Avaliação de Matemática - 3,0"), not AI-generated — `disciplina` is a free-text field (default empty, e.g. "Matemática" or "História") rather than hardcoded, since the app is not tied to one subject. "Aluno(a)" is intentionally left blank in `ExamPaper` (a printed line) for the student to fill in by hand.

### Error handling

`LlmApiError` (in `llmClient.ts`) carries an HTTP status and a Portuguese, user-facing message, thrown by both `callAnthropic()` and `callGemini()`. Known cases (invalid key, rate limit/quota, bad request, network failure, missing tool-call in the response) get specific messages per provider — the two providers report auth failures on different HTTP statuses (Anthropic: 401; Gemini: usually 400 with an "API key not valid" message, or 403), so `callGemini()` pattern-matches the error body rather than relying on status code alone. `App.tsx` catches `LlmApiError` and falls back to a generic message for anything else.
